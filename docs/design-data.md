# 数据模型与导入管线

## 一、为什么现有导入器一定会坏

现有模型大概是：

```
{ 学生, 一次考试, [ 科目 → 分数 / 级名 / 班名 ] }
```

而真实的期中表是：

```
{ 学生, 两次考试, [ 科目 → (上次级名, 本次分数, 本次级名) ], 分层, 导师 }
```

差的三个维度：**考试次别、排名池、导师**。这不是调正则能补的，是模型不对。

### 实测结论（基于 `10班期中.xlsx`，33 名学生）

1. 表头里的 `1` / `2` 是**考试次别**：`1` = 上一次考试，`2` = 本次期中。
   验证：`浮动 = 级名1 − 级名`，33/33 成立；`期中总分 = 四科分数2 之和`，33/33 成立。
   所以 `浮动` 是**派生列**，不是原始数据。

2. **数学、英语按「层」排名，池子跨班。**
   验证：二层（2A+2B 合并）按分数降序，名次 0 处逆序；一层同理。
   名次范围到 208，而本班二层只有 23 人 → 池子是全年级（或全区）同层学生。

3. **语文、物理按「全年级」排名**，不分层（名次范围 9–390）。

4. 同分同名次（数据内 0 处反例）。

> 由此：**不同科目的名次不能并排比较。**
> 数学「第 5 名」是二层池约 200 人里的第 5；语文「第 120 名」是全年级约 400 人里的第 120。

## 二、核心实体

```
School
 └ Class
    └ Student
       ├ Enrollment      (分包、分层归属，随学期变)
       └ Record          (沟通 / 谈心 / 日常，时间线)
 └ Exam                 (考试次别：label + date + order)
    └ SubjectScore
RankPool                (一等概念，见下)
Template                (学校格式的列映射，可导出分享)
```

### RankPool —— 这个模型的核心

```
RankPool {
  subject:  科目
  tier:     1 | 2 | null      // null = 不分层
  scope:    'grade' | 'tier'
  size:     池内人数（可选）
}

SubjectScore {
  studentId, examId, subject
  rawScore: number
  rank:     number
  poolId:   RankPool         // 名次属于哪个池
}
```

### 不变量（写进代码，不要只写进文档）

1. **名次只在同一个 `poolId` 内可比。** 跨池比较一律视为编程错误。
2. **展示名次必须带池标签。** 「二层内第 5 名」，不能只写「第 5 名」。
3. **派生值不落库。** `浮动`、总分、班均分、覆盖率，全部实时计算。
4. **`浮动` 可比的前提是两次考试的池一致。** 池变了要标记为「不可比」而不是算出差值。

## 三、导入管线：四段，每段是纯函数

```
detect ──→ map ──→ confirm ──→ commit
(探测)     (映射)    (确认)      (落库)
```

| 段 | 输入 | 输出 | 谁决定 |
| :-- | :-- | :-- | :-- |
| detect | 原始表格（二维数组） | 结构草图：列分组、疑似次别、疑似派生列、置信度 | 全自动 |
| map | 结构草图 + 模板库 | 列 → 语义的映射建议 | 模板优先，AI 兜底 |
| confirm | 映射建议 | 用户确认后的映射 | 唯一需要人的一段 |
| commit | 映射 + 数据 | 落库 + 校验报告 | 全自动 |

**每段都不能有 DOM、不能有 React。** 这样它们能单测，也能被夜间自动化验证。

### 模板（Template）

模板是 `map` 段的持久化产物：

```json
{
  "name": "某校期中表 v1",
  "match": { "columns": ["姓名", "班级", "总分1", "级名1", "..."], "headerRows": 1 },
  "mapping": [
    { "col": 1,  "role": "student.name" },
    { "col": 5,  "role": "exam.total",      "attempt": 2 },
    { "col": 11, "role": "tier",            "subject": "数学" },
    { "col": 13, "role": "score",           "subject": "数学", "attempt": 2 },
    { "col": 14, "role": "rank",            "subject": "数学", "pool": "tier" }
  ]
}
```

- 模板只存**列名到语义**的映射，**不含任何学生数据**
- 可导出、可分享、可随仓库分发
- 命中模板 → 老师什么都不用做；未命中 → 指两下，生成新模板

**这才是「支持不同学校」的正确形态**：个性化在模板层，不在密钥层。
不给老师配 API key，不把成绩上传到任何地方。

## 四、存储

现状是 `localStorage`。两个问题：

1. **5MB 上限。** 33 学生 × 多年考试 × 每条记录，两三年就顶满。
2. **同步阻塞。** 大对象读写会卡主线程。

建议迁移到 **IndexedDB**（异步、配额按存储空间给）。迁移方式：

```
读 localStorage（旧键） → 写 IndexedDB → 保留旧键一个版本做回退 → 下个版本删
```

注意：Capacitor 下 WebView 的持久化以 `applicationId` 为界。
**改包名 = 数据目录变更 = 老数据读不到。** 迁移唯一可靠路径是：
导出 JSON → 改包名 → 装新包 → 导入 JSON。

## 五、分层与导师

- `分层` 只是**归属标签**（1层/2层 + A/B 区），它决定排名池，不决定能力高低
- `导师` 是真实维度（两位老师），对应现有的「分包」概念，要提到 `Student.Enrollment` 里
